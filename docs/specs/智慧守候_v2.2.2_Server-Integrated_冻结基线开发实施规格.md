# 0. v2.2.2 修订说明

## 0.1 已保留的 v2.2/v2.2.1 核心结论

以下已评审通过的原则全部保留：

1. `operating_mode + activity + fault_codes` 为唯一设备状态模型；
2. 完整浇水决策只在云端，Pi 只执行命令和版本化 `fallback_policy`；
3. LLM 不输出最终水量、泵时长、脉冲数或 GPIO；
4. `claim_ttl_sec` 只约束未领取命令，`session_max_duration_sec` 约束领取后的执行会话；
5. Pi SQLite 水量台账是硬限额权威，云端为审计和预检查；
6. 不使用“湿度差 × mL/百分点”推算整盆缺水量，采用小剂量脉冲闭环；
7. 普通单向阀不作为正向防虹吸装置；
8. PostgreSQL jobs + 独立 Worker 承担慢任务；
9. real/demo/test/mock 数据严格区分；
10. 小米 BLE 不兼容时可切换有线温湿度 Provider；
11. 主控植物和活跃补水命令由数据库部分唯一索引兜底；
12. Stage 2 设备链路打通当天即开始真实只读遥测。

## 0.2 本版依据

v2.2.2 同时吸收两类新证据：

- 对 v2.2.1 开发包的外部评审，重点覆盖回滚、migration、鉴权硬门、HTTPS 开发路径、备份和语音旁路安全；
- 2026-09-13 对实际共享服务器和 aibot 的八份只读审计报告，存放于 `docs/server-audit/`。

审计确认：当前服务器为 Debian 13、2 vCPU、约 7.5 GiB RAM；现有 Nginx 占用 80/443；aibot 以 systemd 方式运行于 `/opt/asist-embodiment`，现有生产目录存在未提交漂移；宿主机当前未安装 Docker、未发现运行中的 PostgreSQL；Tailscale 与 OpenVPN 均在运行。

## 0.3 Server-Integrated 冻结决策

1. **同机、业务独立**：Flower 与 aibot 使用同一物理服务器，但不共享业务数据库、命令路径、设备 token、会话或运行目录。
2. **aibot 保持现状**：本项目不得顺带迁移、重构、reset、clean 或容器化现有 aibot。
3. **Flower 独立 Compose**：生产四服务固定为 `proxy / api / worker / postgres`，Compose project 为 `flower-prod`。
4. **宿主 Nginx 唯一公网入口**：80/443 继续由宿主 Nginx 占用；Flower 内部 proxy 只映射 `127.0.0.1:18080`。
5. **域名独立**：正式建议 `flower-api.bkeel.com`，不放入 `cs.bkeel.com/api`。
6. **开发/生产目录分离**：`/root/flower` 为开发 Git 仓库；生产使用 `/srv/flower/releases/<git-sha>` + `/srv/flower/current` + `/srv/flower/shared/`。
7. **固定镜像发布**：应用镜像使用 commit SHA tag；回滚不得依赖被覆盖的 `latest`。
8. **migration 显式执行**：生产 migration 是唯一受控一次性步骤，不在 API/Worker entrypoint 自动运行。
9. **生产配置 fail-closed**：`DEV_AUTH_BYPASS=true`、`DEV_MODE=true` 或非 HTTPS 公网基址在 production 下均导致启动失败。
10. **Worker 初始并发 1**：2 vCPU 主机以外部 AI Provider 为主，不在当前 MVP 同机新增本地 LLM 或持续云 ASR。
11. **语音绝不绕过 Flower 安全链**：aibot peripheral、语音助手、本地 HTTP 调试接口和通用 Agent 均不得直接驱动 GPIO17/YYMOS。
12. **未来平台化分期**：ASR/TTS/LLM 能力服务、统一输入和 Device Registry 均属于后续阶段，不进入当前单盆花 MVP。

## 0.4 网络与共享宿主机安全

- 正式 Pi 业务链路：Pi 主动 HTTPS 访问 Flower 域名，不要求家庭网络开放入站端口；
- Tailscale 近期主要用于维护。正式域名尚未就绪时，开发联调可通过 Pi 主动建立的 SSH/Tailscale 加密隧道访问服务器环回开发端口；禁止 `verify=False`；
- 首次安装 Docker 会改变 bridge/NAT/转发规则，必须在变更前后回归 UFW、nftables、Tailscale、OpenVPN、City Front WebSocket 和 aibot；
- Flower 生产只发布 `127.0.0.1:18080`，API 8000 与数据库 5432 不发布宿主端口；
- 当前宿主机 8000 虽无监听但已被 UFW 放行，禁止将开发 API 绑定 `0.0.0.0:8000`。

## 0.5 外部上线前置项

正式微信小程序上线前必须真实确认：Flower 域名 DNS/TLS、微信后台 request/upload/download 合法域名、AppID/AppSecret，以及按实际托管地区和当期平台规则适用的备案/主体要求。未完成前可使用 Mock、开发版或体验版推进，但不得标记正式上线完成。

# 1. 项目概述

## 1.1 项目名称

**智慧守候·AI植物守护与记忆灌溉系统**（暂定名）

## 1.2 项目定位

本项目是一套软硬件结合的 AI 物联网作品。系统通过摄像头拍摄植物，由云端识别植物品种并检索可信养护资料；再结合真实土壤湿度、空气温湿度、所在地天气、放置环境、花盆信息和家庭养护经验，生成可解释的养护策略。树莓派负责读取真实传感器、执行本地安全检查，并控制低压蠕动泵完成分次、限量的闭环补水。

项目不只是“自动浇花器”，而是一套“记忆守候系统”：把长辈留下的照片、故事和养花经验保存下来，让这些经验经过用户确认后真正参与养护策略，并在每次生效时留下可见记录。

## 1.3 创作背景

项目源于创作者的真实家庭经历：外公生前喜欢养花，日常照料茉莉、山茶、月季和君子兰。外公去世后，部分植物因为无人持续照料而逐渐枯萎。

项目希望回答：

> 能否让机器认出植物、理解它在当地应该怎样生长、记住家人的经验，并在无人照顾时继续安全地守护它？

项目核心路径是：

**看见植物 → 认识植物 → 获取知识 → 感知环境 → 作出判断 → 少量补水 → 再次检测 → 保存记忆。**

## 1.4 目标用户

- 经常出差、无法持续照顾家庭绿植的人；
- 异地工作、希望远程照顾老家植物的人；
- 喜欢养花但缺乏系统园艺知识的人；
- 希望保存亲人养护经验和家庭故事的人；
- 后续可扩展到喂鱼、菜园、补光等家庭自动照料场景。

## 1.5 一句话介绍

> “智慧守候”通过摄像头识别植物，联网学习它在当地的养护知识，再结合真实土壤湿度、环境温湿度、天气和家人留下的经验，判断什么时候需要补水，并由树莓派和蠕动泵安全执行，让家庭经验在 AI 时代继续发挥作用。

# 2. 项目目标与非目标

## 2.1 首版 MVP 必须完成

1. 树莓派 4B 连接 USB 摄像头并按需拍摄植物图片；
2. 云端植物识别返回 Top 3 候选、学名和置信度；
3. 用户必须在小程序中确认品种，或手动输入植物名称；
4. 云端按学名检索至少 2 个可信养护来源并保存来源信息；
5. 用户录入城市、放置环境、花盆尺寸、材质和排水孔信息；
6. 获取并缓存当地天气；
7. 树莓派读取 ADS1115 与电容式土壤湿度传感器；
8. 优先读取小米 BLE 温湿度计，失败时允许切换 SHT30/AHT20；
9. 读取 P451 浮球水位开关，缺水立即禁止开泵；
10. 通过 YYMOS-1 控制 12V 蠕动泵；
11. 完成土壤传感器、泵流量和停泵滴漏标定；
12. 自动浇水采用小剂量脉冲闭环；
13. 小程序显示实时状态、养护卡、守候记录和可验证的数据趋势；
14. 支持安全的手动补水，但不能绕过本地安全规则；
15. 保存家庭照片、故事和经验，并让已确认经验参与策略；
16. 自有云服务器通过 Docker Compose 部署；
17. 树莓派端通过 systemd 开机自启动；
18. 关键行为均有结构化日志和人话时间线；
19. 提供小程序内告警中心；微信订阅消息可后补；
20. 提供离线演示模式，但不得把演示数据冒充真实数据。

## 2.2 首版明确不做

- 不训练自己的植物识别模型；
- 不做摄像头云台；
- 不做连续视频流；
- 不做病虫害诊断；
- 不做多盆自动切换水路；
- 不做自动施肥和自动温控；
- 不做实验室级流量计；
- 不做 MQTT；
- 不做 Redis、Kafka、Celery、Kubernetes；
- 不做复杂运营后台；
- 不做多用户共享设备权限体系；
- 不让 LLM 输出水量、时长、脉冲数或 GPIO 指令；
- 不把传感器百分比包装成绝对土壤含水率；
- 不把模拟趋势曲线标记为真实数据。

# 3. 核心设计原则

## 3.1 云端负责理解，本地负责安全执行

云端负责：

- 植物识别；
- 养护知识检索；
- 天气数据；
- LLM 结构化；
- 完整决策引擎；
- 生成本地保守策略；
- 小程序业务；
- 数据持久化和告警。

树莓派负责：

- 真实传感器采集；
- 水位和泵状态检查；
- 指令幂等与过期检查；
- 本地限额；
- 泵开关和脉冲执行；
- 断网时执行云端预先生成的保守策略；
- 异常时默认关泵。

## 3.2 AI 只提供知识，不直接控制硬件

LLM 可以：

- 识别或辅助识别植物；
- 提取公开养护资料；
- 把家庭经验整理成结构化规则；
- 生成人类可读说明草稿。

LLM 不可以：

- 直接决定水泵运行秒数；
- 直接生成 GPIO 指令；
- 绕过用户确认；
- 绕过服务器和树莓派的安全门；
- 把没有来源支持的精确数值当作事实。

## 3.3 所有不确定情况默认不浇水

- 水位未知：不浇；
- 土壤传感器故障：不自动浇；
- 时间不可信：不浇；
- 标定缺失：不浇；
- 命令来源无法验证：不执行；
- 泵状态未知：先关泵；
- 本地保守策略过期：进入安全保持；
- 数据冲突：采用更少水、更晚浇的方案并提示用户。

## 3.4 真实数据与演示数据严格分开

所有曲线、事件和识别结果必须带数据来源：

```text
real            真实运行数据
demo            明确标识的演示数据
imported_test   受控测试导入数据
mock            开发 Mock 数据
```

任何界面都不得把 `demo/mock` 隐藏成真实数据。

## 3.5 版本单一来源

开发仓库只能有一个当前需求入口：

```text
SPEC_CURRENT.md  → v2.2.2 内容
```

旧版本放入：

```text
docs/archive/v2.0.md
docs/archive/v2.1.md
```

README、开发 Prompt、验收报告和代码注释一律引用 v2.2.2；v2.0、v2.1、v2.2、v2.2.1 仅可归档，不得作为实现输入。

## 4.1 Docker 服务

生产环境使用 4 个 Flower Compose 服务：

```text
proxy
api
worker
postgres
```

宿主机现有 Nginx 继续独占 80/443，并以独立虚拟主机将 `flower-api.bkeel.com` 反向代理到 `127.0.0.1:18080`。Compose 内部 `proxy` 只监听容器 8080 并映射到宿主环回地址，不申请证书、不抢占 80/443。

`api` 与 `worker` 使用同一后端镜像，只是启动命令不同，因此不会造成两套代码。

## 4.2 通信方式

生产业务流量使用 HTTPS：

- 正式环境统一使用 `https://flower-api.bkeel.com`（域名可替换，但必须是有效 HTTPS）；
- 树莓派每 30 秒上报一次状态；
- 树莓派每 3-5 秒调用命令领取接口；
- 命令执行后立即上报结果；
- 图片仅在识别时上传；
- 小程序只访问云服务器，不直接访问家庭局域网；
- 后续设备增多时再评估 MQTT 适配层。

**开发期无正式域名时的安全例外**：优先使用 Pi 主动建立的 SSH/Tailscale 加密隧道，将 Pi 本地环回端口转发到服务器开发代理的环回端口；Pi 只访问本地 `127.0.0.1`。禁止使用 `verify=False` 绕过 TLS 校验，也禁止把开发 HTTP 端口直接公开到公网。生产环境不得使用该例外。

# 5. 唯一设备运行状态模型

v2.2.2 禁止再定义一套并行的 `device_state` 枚举。系统使用三个互不重叠的维度。

## 5.1 operating_mode：唯一自动化等级

```text
STARTING
FULL
LOCAL_CONSERVATIVE
SAFE_HOLD
```

- **STARTING**：正在启动和自检；禁止浇水。
- **FULL**：云端在线且关键安全条件满足；云端可生成自动命令，用户可手动补水。
- **LOCAL_CONSERVATIVE**：云端短时离线，但本地保守策略仍有效；仅允许本地保守单脉冲自动补水。
- **SAFE_HOLD**：任一关键条件不可信；禁止所有浇水，只采集和告警。

## 5.2 activity：当前活动

```text
IDLE
CAPTURING
CALIBRATING
WATERING
```

`activity` 只说明设备正在做什么，不表示安全级别。

## 5.3 fault_codes：故障与降级原因

可同时存在多个：

```text
LOW_WATER
SOIL_SENSOR_FAULT
TIME_UNTRUSTED
CALIBRATION_MISSING
PROFILE_MISSING
PROFILE_STALE
CLOUD_OFFLINE
BLE_STALE
CAMERA_UNAVAILABLE
PUMP_DRIVER_SUSPECT
LOCAL_POLICY_EXPIRED
DISK_ERROR
```

其中硬阻断故障为：

```text
LOW_WATER
SOIL_SENSOR_FAULT
TIME_UNTRUSTED
CALIBRATION_MISSING
PROFILE_MISSING
LOCAL_POLICY_EXPIRED
PUMP_DRIVER_SUSPECT
```

`BLE_STALE` 和 `CAMERA_UNAVAILABLE` 不阻断已有植物的安全补水，只影响识别或环境修正。

## 5.4 命令来源与开泵权限函数

### 5.4.1 唯一命令来源枚举

所有代码、数据库和 API 只能使用以下 `source` 值：

```text
cloud_auto       云端完整决策引擎创建的自动补水
user_manual      用户在小程序发起的手动补水或拍照
local_fallback   Pi 在 LOCAL_CONSERVATIVE 下执行的缓存策略
maintenance_test 本机显式诊断/标定测试；不得由远程 API 创建
```

运行环境另用 `run_mode` 表示，合法值仅为：

```text
real / demo / offline_demo
```

`source` 与 `run_mode` 不得混用，也不得在其他章节创造别名，如 `manual`、`auto` 或 `demo_auto`。

### 5.4.2 唯一开泵权限函数

设备端只能通过一个纯函数判断是否允许开泵：

```text
can_dispense(source):
  activity 必须为 IDLE
  不得存在硬阻断 fault_code
  source in {cloud_auto, user_manual} 时 operating_mode 必须为 FULL
  source == local_fallback 时 operating_mode 必须为 LOCAL_CONSERVATIVE，且 fallback_policy 合法、未过期
  source == maintenance_test 时必须由本机显式 --pump-test 发起，最长 1 秒，且水位正常
  operating_mode in {SAFE_HOLD, STARTING} 时永远 false
```

不得在多个模块复制不同版本的允许规则。远程接口不得创建 `maintenance_test` 命令。

# 6. 核心业务流程

## 6.1 新增植物

1. 小程序创建待识别植物；
2. 小程序请求树莓派拍照；
3. 服务器创建 `camera/capture` 命令；
4. 树莓派拍摄整株、叶片近景和花朵/果实照片；
5. 图片经过亮度、清晰度和大小检查后上传；
6. 服务器创建植物识别 Job；
7. Worker 调用识别 Provider，返回 Top 3；
8. 用户确认候选或手动输入名称；
9. 用户填写位置、花盆、排水信息；
10. 服务器创建养护研究 Job；
11. Worker 检索至少 2 个来源并用 LLM 结构化；
12. 小程序展示来源、冲突和风险提示；
13. 用户确认养护卡；
14. 服务器生成正常策略和本地保守 `fallback_policy`；
15. 树莓派完成标定后，用户才能开启自动守护。

## 6.2 FULL 模式自动守护

```text
树莓派采集并上传数据
        ↓
服务器校验数据新鲜度与设备状态
        ↓
云端唯一决策引擎计算 water / hold / defer
        ↓
若需要补水，调用唯一 create_command()
        ↓
设备领取命令并进行本地安全校验
        ↓
执行一个脉冲
        ↓
关泵、等待滴漏稳定和土壤吸收
        ↓
重新测量
        ↓
达到目标或达到上限则停止
否则执行下一脉冲
```

## 6.3 LOCAL_CONSERVATIVE 模式

Pi 不运行云端完整决策算法，只读取云端预先生成的 `fallback_policy`：

```json
{
  "policy_version": 7,
  "profile_version": 3,
  "generated_at": "2026-09-03T08:00:00Z",
  "valid_until": "2026-09-10T08:00:00Z",
  "trigger_soil_below_pct": 28,
  "min_interval_hours": 12,
  "pulse_ml": 10,
  "max_pulses": 1,
  "max_session_ml": 10,
  "max_24h_ml": 60,
  "timezone": "Asia/Shanghai",
  "allowed_windows_local": [["06:00", "09:00"], ["17:00", "20:00"]],
  "profile_hash": "sha256:..."
}
```

进入条件：

- 最近一次云端通信在 5-60 分钟前；
- 时间可信；
- 土壤和水位传感器健康；
- fallback_policy 未过期；
- 标定完整。

Pi 只做简单比较，不重新计算天气、温度、花盆和家庭经验修正。这些已由云端编译进策略。

`timezone` 必须是合法的 IANA 时区名称。Pi 使用 Python `zoneinfo.ZoneInfo(policy.timezone)` 将可信 UTC 时间转换为策略当地时间后判断 `allowed_windows_local`。时区缺失、非法或无法加载时，策略判定为无效并进入 SAFE_HOLD。首版不允许时间窗跨越午夜；确有需要时拆成两个区间。

## 6.4 手动补水

小程序只允许传入：

```text
1 份
10mL
20mL
30mL
系统允许范围内的自定义 mL
```

不允许输入运行秒数。

服务器返回 `pending` 只表示指令已创建；必须等设备上报 `succeeded` 才显示“浇水完成”。

手动补水仍受以下约束：

- 设备必须 FULL；
- 水位正常；
- 泵空闲；
- 时间可信；
- 标定完整；
- 未超滚动 24 小时上限；
- 未超单次上限；
- 命令未过期。

## 6.5 家庭记忆

用户可保存：

- 长辈照片；
- 故事；
- 原始养护经验；
- 经验适用植物；
- AI 结构化规则；
- 用户确认和启停状态。

例如：

> 外公说茉莉夏天不要中午浇，土干了傍晚少量浇。

结构化为：

```json
{
  "preferred_windows": [["18:00", "21:00"]],
  "watering_style": "small_portions",
  "soil_preference": "let_surface_dry",
  "source_type": "family_memory",
  "requires_confirmation": true
}
```

家庭经验可以改变时间偏好、脉冲大小和触发阈值，但不能覆盖缺水、传感器故障、限额和最大连续开泵时长。

每次经验实际改变决策时，必须产生 `memory_rule_applied` 事件，并在小程序中显示人话说明。

## 7.2 正确的防虹吸水路

```text
             花盆及出水喷嘴
          ┌────────────────┐
          │ 喷嘴悬空在土面上 │ ← 出水口开放，不能插入土中
          └───────▲────────┘
                  │
                  │ 出水管，机械固定
            ┌─────┴─────┐
            │ 12V蠕动泵  │
            └─────▲─────┘
                  │
                  │ 进水管
      ┌───────────┴───────────┐
      │      透明储水桶         │
      │  最高液位低于喷嘴≥5cm   │
      │  P451位于低水位位置     │
      └───────────────────────┘
```

必须同时满足：

1. 储水桶最高液位低于最终出水喷嘴至少 5cm；
2. 喷嘴在自由空气中，距土面约 1-2cm；
3. 喷嘴不得埋入土壤或浸入积水；
4. 管路用管夹固定，不能因搬动而垂落到水桶液位以下；
5. 泵停后 10 分钟无连续水流，滴漏总量不超过 3mL；
6. 首版禁止接自来水压力管路。

普通单向阀朝花盆方向安装时不能阻止正向虹吸，只能减轻回流。只有专用防虹吸阀、真空破坏器、开放空气间隙或满足高度差，才能作为防虹吸措施。

## 7.3 树莓派 40Pin 分配

```text
Pin 1  / 3.3V        → ADS1115 VDD
Pin 3  / GPIO2 SDA   → ADS1115 SDA
Pin 5  / GPIO3 SCL   → ADS1115 SCL
Pin 6  / GND         → ADS1115 GND
Pin 9  / GND         → 土壤传感器 GND
Pin 11 / GPIO17      → YYMOS-1 PWM
Pin 13 / GPIO27      → P451 线1
Pin 14 / GND         → YYMOS-1 GND
Pin 17 / 3.3V        → 土壤传感器 VCC（确认支持3.3V后使用）
Pin 20 / GND         → P451 线2
```

### ADS1115 与土壤传感器

```text
Pin 1  → ADS1115 VDD
Pin 3  → ADS1115 SDA
Pin 5  → ADS1115 SCL
Pin 6  → ADS1115 GND

Pin 17 → 土壤传感器 VCC
Pin 9  → 土壤传感器 GND
土壤传感器 AOUT → ADS1115 A0
ADS1115 ADDR → GND，地址 0x48
```

ADS1115 增益初始使用 `GAIN_1`，最终以实测电压范围为准。

### YYMOS-1 与水泵

```text
控制侧：
Pin 11 / GPIO17 → YYMOS-1 PWM
Pin 14 / GND    → YYMOS-1 GND
GPIO17 与 GND 之间并联 10kΩ 下拉电阻

动力侧：
12V 电源+ → YYMOS-1 电源输入+
12V 电源- → YYMOS-1 电源输入-
YYMOS-1 输出+ → 蠕动泵+
YYMOS-1 输出- → 蠕动泵-
```

12V 电源负极与树莓派 GND 必须共地，12V 正极不得接入树莓派任何针脚。

### P451 水位开关

```text
P451 线1 → Pin 13 / GPIO27
P451 线2 → Pin 20 / GND
```

GPIO27 使用内部上拉，并尽量设置为：

```text
有水且线路正常：LOW
缺水或断线：HIGH
```

去抖规则：

- 从有水到缺水：连续 5 次一致，每次间隔 200ms，立即进入缺水；
- 从缺水恢复有水：必须持续稳定 10 秒后恢复。

## 7.4 泵流量、滴漏与最低可控剂量标定

泵的 217mL/min 只能作为参考。

流量标定：

1. 固定水桶、管路和喷嘴位置；
2. 泵运行 10 秒，量杯接水；
3. 重复 3 次；
4. 极差必须不超过平均值 15%；
5. 计算 `pump_flow_ml_per_sec`。

滴漏标定：

1. 水桶加至最高工作液位；
2. 开泵 5 秒后关泵；
3. 静置 10 分钟，记录停泵后滴漏量；
4. 重复 3 次；
5. 保存 `pump_afterdrip_mean_ml`（3次平均值）和 `pump_afterdrip_max_ml`（3次最大值）；
6. `pump_afterdrip_max_ml <= 3mL` 才通过防虹吸/滴漏验收；平均值只用于剂量估算，最大值只用于安全判定与误差展示。

另需记录最短稳定运行时间 `pump_min_run_sec`。

最低可控脉冲量：

```text
min_controllable_ml =
  pump_flow_ml_per_sec × pump_min_run_sec + pump_afterdrip_mean_ml
```

估算单个脉冲运行时间：

```text
run_sec = max(
  pump_min_run_sec,
  (pulse_ml - pump_afterdrip_mean_ml) / pump_flow_ml_per_sec
)
```

不得使用“目标量小于滴漏量时不开泵但认为滴漏可满足”的逻辑；没有启动泵就不会产生该次滴漏。若请求量低于最低可控剂量，应拒绝或上调为最低安全脉冲，并明确告知。UI 中的毫升数必须标注为“基于标定的估算量”，不得宣传为实验室计量精度。

## 7.5 土壤湿度标定

保存：

```text
adc_dry
adc_wet
insert_depth_mark
calibrated_at
```

要求：

- 使用实际种植介质；
- 干湿值差应足够明显；
- 记录并固定插入深度；
- 换土、换盆或重新插入后重新标定；
- 采用 5 点窗口中位数；
- 连续异常才判定故障；
- UI 称为“相对土壤湿度”，不称绝对含水率。

## 7.6 硬件安全边界

- 树莓派和水泵使用独立电源；
- 所有接线在断电状态完成；
- 电子模块位于水桶和花盆上方并装入防溅盒；
- 水桶容量不超过 2L；
- 接水盘容量不小于水桶容量；
- 泵默认关闭；
- 任何异常优先关泵；
- 缺水为硬阻断；
- 12V 回路建议增加 1A 保险；
- YYMOS-1 若无感性负载保护，增加续流二极管；
- GPIO 回读只能证明控制引脚已拉低，不能证明泵电机实际断电；不得在答辩或文档中把 GPIO 回读描述成电流反馈。

产品化升级可增加：独立硬件定时切断模块、电流传感器、漏水传感器和 RTC。

## 8.4 BLE 温湿度 Provider

小米温湿度计不是安全关键路径，也不是 MVP 的硬阻塞项。

### 8.4.1 探测流程

提供：

```bash
./ble_probe.sh
```

输出：

```text
发现的 MAC
广播名称
推测型号
是否存在可解析温湿度字段
是否加密
是否需要 bindkey
最近一次有效数据时间
```

状态：

```text
READY
BINDKEY_REQUIRED
UNSUPPORTED_MODEL
NO_ADVERTISEMENT
STALE
```

### 8.4.2 加密型号

若库存固件广播加密，必须提供正确 bindkey 才能被动解密。配置：

```text
XIAOMI_DEVICE_MODEL=
XIAOMI_DEVICE_MAC=
XIAOMI_BINDKEY=
```

软件不得假设“被动监听就一定不需要密钥”。

### 8.4.3 备用方案

以下任一条件成立，就切换 SHT30/AHT20：

- 型号不支持；
- 无法合法获得 bindkey；
- 连续 30 分钟有效数据不足要求；
- 比赛前压力测试不稳定。

备用传感器只增加一个 Provider，不改变决策和数据库结构。

## 8.5 摄像头与 BLE 并发

Pi 4 的板载蓝牙并不与 USB 摄像头共用同一 USB 总线，因此不把“总线争用”列为架构缺陷。但仍应控制资源：

- 摄像头只按需拍照，不连续预览和上传；
- 摄像头任务与 BLE 任务分离；
- 拍照前丢弃前 5 帧；
- USB 摄像头优先接 USB 2.0 口；
- 使用可靠 5V 3A 电源；
- 拍照时 BLE 允许短暂漏包，但最近数据仍可用；
- 完成 30 分钟“持续 BLE 扫描 + 每分钟拍照”压力测试。

## 8.6 传感器采样

默认值均可配置：

```text
土壤：10秒一次
水位：1秒一次
空气温湿度：广播到达即更新，5分钟 stale
遥测：30秒一次
命令领取：5秒一次
```

土壤触发必须满足：

- 最近 5 次中至少 3 次有效；
- 使用有效值中位数；
- 不能由单个跳变触发；
- 连续 5 次无效进入 `SOIL_SENSOR_FAULT`。

## 8.7 时间与滚动 24 小时限额

### 8.7.1 时间使用原则

- 同一次开机内的持续时间计算：使用 `time.monotonic()`；
- 跨重启的 24 小时窗口：使用可信 UTC 时间；
- 时间不可信时：进入 SAFE_HOLD，不允许产生新的浇水记录；
- 不能宣称单调时钟可跨重启。

### 8.7.2 水量台账

本地 SQLite 记录：

```sql
CREATE TABLE water_ledger (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  command_id TEXT UNIQUE,
  source TEXT NOT NULL,
  state TEXT NOT NULL,
  reserved_ml REAL NOT NULL,
  actual_ml REAL,
  quota_ml REAL NOT NULL,
  server_issued_at_utc TEXT,
  trusted_wall_time_utc TEXT,
  recovered_at_utc TEXT,
  boot_id TEXT NOT NULL,
  monotonic_started REAL,
  monotonic_finished REAL,
  created_at TEXT NOT NULL
);
```

状态：

```text
reserved
final
provisional
reconciled
```

### 8.7.3 预扣与恢复

1. 开泵前先写入 `reserved`，按目标会话最大量预扣；
2. 每个脉冲后更新实际量；
3. 正常结束改为 `final`；
4. 进程或设备中断时改为 `provisional`，暂按预扣量占用额度；
5. 恢复时间与云端后，根据 `server_issued_at_utc` 或云端命令记录对账；
6. 若没有任何可信历史时间，则以首次恢复可信时间作为 `recovered_at_utc`；
7. 这类不确定记录从 `recovered_at_utc` 起保守计入 24 小时，同时产生告警；
8. 不允许永久计入；也不允许恢复后立即清零。

这样既不会因一次时钟异常永久禁用设备，也不会通过重启逃避限额。

## 8.8 命令领取、执行会话与超时

设备领取：

```text
POST /api/v1/device/commands/claim
```

### 8.8.1 两种超时必须分开

- `claim_ttl_sec`：命令创建后等待设备领取的最长时间。只适用于 `pending` 状态；默认 60 秒。
- `session_max_duration_sec`：设备领取并开始后，整次多脉冲会话允许的最长时间。适用于 `executing` 状态；不得复用领取 TTL。

服务端按命令参数计算会话时长：

```text
session_max_duration_sec = min(
  SESSION_MAX_DURATION_HARD_SEC,
  max_pulses × max_continuous_sec
  + max_pulses × (PUMP_AFTERDRIP_SETTLE_SEC + absorb_wait_sec)
  + SESSION_SAFETY_MARGIN_SEC
)
```

REAL 模式在 3 个脉冲、每次 10 秒、30 秒滴漏稳定和 300 秒吸收等待时，建议默认上限约 1200 秒；DEMO 模式可更短。领取 TTL 到期只会使未领取命令 `expired`，**不得在执行中途因 60 秒领取 TTL 到期而停止会话**。

命令例：

```json
{
  "id": "uuid",
  "device_id": "garden-001",
  "capability": "dispenser",
  "action": "dispense",
  "parameters": {
    "target_ml": 20,
    "pulse_ml": 10,
    "max_pulses": 2,
    "max_continuous_sec": 10,
    "afterdrip_settle_sec": 30,
    "absorb_wait_sec": 300,
    "wait_after_pulse_sec": 330
  },
  "source": "cloud_auto",
  "run_mode": "real",
  "policy_version": 7,
  "issued_at_server": "ISO8601",
  "claim_ttl_sec": 60,
  "claim_deadline_at": "ISO8601",
  "session_max_duration_sec": 900
}
```

### 8.8.2 状态与截止时间

```text
pending --领取成功--> claimed --started--> executing
pending 超过 claim_deadline_at                  → expired
claimed 超过 COMMAND_START_GRACE_SEC 未 started → failed(claim_abandoned)
executing 超过 session_deadline_at              → timed_out
```

设备调用 `started` 后，服务端设置：

```text
session_deadline_at = started_at + session_max_duration_sec
```

Pi 同时用本地单调时钟建立会话截止点，在每个脉冲前、等待期间和下一次脉冲前检查；达到截止时间立即关泵并报告 `session_timeout`。每个脉冲后上报 `progress`，供小程序展示和服务端识别卡死，但 progress 不延长绝对会话截止时间。

设备执行前必须检查：

- 命令 ID 未执行；
- 命令属于本设备；
- 命令在领取时未超过 `claim_ttl_sec`；
- `source` 属于唯一枚举；
- operating_mode 允许该来源；
- activity 为 IDLE；
- 无硬阻断 fault；
- 水位正常；
- 标定完整；
- 本地 24 小时额度足够；
- 参数未超过本地硬上限；
- `session_max_duration_sec` 不超过本地硬上限。

## 8.9 泵控制与看门狗

第一版只做 100% 开/关，不做 PWM 调速。

每个脉冲：

```text
wait_after_pulse_sec = PUMP_AFTERDRIP_SETTLE_SEC + absorb_wait_sec

run_sec = max(
  pump_min_run_sec,
  (pulse_ml - pump_afterdrip_mean_ml) / pump_flow_ml_per_sec
)
```

其中 `pump_afterdrip_mean_ml` 用于估算，`pump_afterdrip_max_ml` 只用于安全合格判定。REAL 默认 `30 + 300 = 330` 秒；DEMO 默认 `30 + 45 = 75` 秒。

但必须满足：

```text
run_sec >= pump_min_run_sec
pulse_ml >= min_controllable_ml
run_sec <= max_continuous_sec
```

泵控制实现：

- 进程内独立定时器防止主循环阻塞；
- 50ms 周期检查水位；
- `try/finally` 关泵；
- SIGTERM/SIGINT 时关泵；
- systemd `Restart=always`、`RestartSec=1`；
- 服务启动第一步拉低 GPIO；
- `ExecStopPost` 调用紧急关泵脚本；
- 记录 GPIO 命令状态，但不得将其当作电机电流反馈。

进程内看门狗不能替代独立硬件断电保护；文档和答辩必须如实说明。

# 10. 唯一完整浇水决策引擎

完整决策引擎只部署在云端。Pi 只执行命令和 fallback_policy。

## 10.1 输入

- 已确认植物；
- 已确认 care_profile；
- 最新土壤相对湿度；
- 空气温湿度及新鲜度；
- 水位；
- 花盆信息；
- 放置环境；
- 天气和降雨；
- 距上次浇水时间；
- 滚动 24 小时用量；
- 家庭经验；
- operating_mode；
- 标定状态。

## 10.2 硬阻断 Gate

任一命中即 `hold`：

```text
水位异常
土壤传感器故障
泵忙
非 FULL 模式下尝试云端/手动命令
care_profile 未确认
自动模式关闭（仅自动流程）
最小间隔未到
滚动24小时额度不足
标定缺失
时间不可信
已有活跃 dispense 命令
```

## 10.3 目标湿度阈值

以 care_profile 为基础，用确定性配置修正：

- 高温：适度提前触发；
- 低温：延后触发；
- 空气干燥：小幅提前；
- 空气潮湿：小幅延后；
- 小盆或陶土盆：小幅提前；
- 无排水孔：明显减量并延后；
- 室外且即将降雨：延后；
- 已确认家庭经验：只在允许范围内修正。

所有修正系数写入配置，并有单元测试。温湿度缺失时使用保守默认，不构成硬阻断。

## 10.4 是否浇水

决策分支必须完备且按以下顺序执行：

```text
1. soil >= effective_min
   → hold

2. soil < effective_min 且适用天气规则判断未来有足量降雨
   → defer(reason=rain_expected)

3. soil < effective_min 且当前位于 allowed_windows_local
   → water(reason=within_window_below_target)

4. soil <= effective_min - URGENT_OVERRIDE_GAP_PCT
   → water(reason=urgent_override_window)  # 可越过偏好时间窗

5. 其余 soil < effective_min 且不在时间窗
   → defer 到下一个允许时间窗
```

`URGENT_OVERRIDE_GAP_PCT` 默认 15，只决定是否可以越过时间偏好，不决定正常时间窗内是否补水。正常场景“低于阈值且在时间窗内”必须直接进入 `water`。

## 10.5 水量与脉冲策略

首版不使用 `湿度差 × mL/百分点`。

初始脉冲按花盆大小配置：

```text
small  默认 10mL，范围 5-15mL
medium 默认 20mL，范围 10-30mL
large  默认 30mL，范围 15-40mL
```

再应用：

- 无排水孔：脉冲和会话上限减半；
- `small_portions` 家庭经验：取范围下限；
- `thorough` 经验：只允许取范围上限，但仍受硬上限；
- LOCAL_CONSERVATIVE：最多一个较小脉冲；
- 单会话最多 3 个脉冲；
- 每次脉冲后等待并重新测量；
- 达到 `effective_min` 立即停止；
- 超过 `effective_max` 记为过量风险并降低后续建议，但首版不自动学习修改参数。

输出例：

```json
{
  "decision": "water",
  "reason": ["soil_below_target", "no_rain_expected"],
  "effective_min_pct": 43,
  "soil_now_pct": 31,
  "pulse_ml": 20,
  "max_pulses": 2,
  "session_max_ml": 40,
  "wait_after_pulse_sec": 330,
  "explain_zh": "土壤相对湿度31%，低于茉莉当前43%的补水触发线，未来12小时无明显降雨，系统将先补水20毫升，等待吸收后再决定是否继续。"
}
```

`explain_zh` 使用模板生成，不调用 LLM。

## 10.6 fallback_policy 生成

云端每次 care_profile 确认或策略更新时，生成保守策略并下发到 Pi。

fallback_policy：

- 不依赖实时天气；
- 使用比正常更低的触发阈值；
- 最小间隔至少 12 小时；
- 单次最多一个小脉冲；
- 24 小时上限为正常上限的 50%；
- 最长有效期 7 天；
- 强制包含 IANA `timezone` 与 `allowed_windows_local`；
- 带 profile_version 和 hash；
- Pi 只接受版本不倒退、时区合法且 Schema 合法的策略。

权威规则：

1. Pi 本地 SQLite `water_ledger` 是**硬件执行与本地滚动24小时限额的权威账本**；
2. 云端 `watering_sessions` 是审计、展示和创建命令前的预检查账本；
3. 服务端创建命令时同时参考云端计算值和设备最近上报的 `used_24h_ml`，按更保守值判断；
4. 对账发现差异时产生 `QUOTA_DIVERGENCE` 告警；在证据未核清前，Pi 使用 `max(local_used, verified_cloud_used)`，云端不得命令 Pi 无条件降低本地已用额度；
5. 只有按 `command_id`、脉冲回执和可信时间完成核验后，才能把 provisional 记录转为 reconciled；
6. 冲突不会永久锁死：无法确定的 provisional 记录按第 8.7.3 节在恢复可信时间后保守占用24小时，再释放额度但保留审计记录。

# 14. 鉴权与安全

## 14.1 设备鉴权

- 每台设备独立 `device_code + device_secret`；
- secret 由部署脚本生成；
- 服务端只存安全哈希；
- 设备换取短期 token；
- token 与 device_id 绑定；
- 支持轮换和吊销；
- 所有设备接口使用 HTTPS。

## 14.2 小程序鉴权

- 微信 code 换 openid；
- 服务端签发自己的会话；
- 所有 plant/device/memory/image 请求统一校验资源归属；
- 生产环境关闭调试绕过；
- `APP_ENV=production` 时若 `DEV_MODE=true`、`DEV_AUTH_BYPASS=true` 或 `APP_BASE_URL` 非 HTTPS，应用必须拒绝启动并返回非零退出码。

## 14.3 语音/外设旁路禁止

任何语音助手、aibot peripheral、本地 HTTP 调试接口、管理后台或通用 Agent 均不得直接或间接驱动 GPIO17、YYMOS 或 pump driver。未来语音只能产生已认证的业务意图；所有非 `local_fallback` 补水仍必须进入 Flower `create_command()`，Pi 端再次经过 `can_dispense()`。

## 14.4 基础防护

- 上传校验 MIME、magic bytes、尺寸和大小；
- 文件名改为 UUID；
- 图片不直接裸露静态目录；
- API key、openid、token 和 secret 日志脱敏；
- ORM 参数化查询；
- 依赖版本锁定；
- 浇水接口限流；
- 命令幂等；
- 设备领取命令必须原子化；
- 图片上传前检查磁盘可用空间，低于 1GiB 拒绝并告警；
- 活跃补水命令和主控植物由数据库部分唯一索引兜底；
- 执行会话超时与领取超时分离。

# 16. 部署要求

## 16.1 Docker Compose 与共享宿主机边界

Flower 生产使用独立 Compose project `flower-prod`，四个服务固定为：

```text
proxy
api
worker
postgres
```

宿主机端口规则：

- 只允许 `127.0.0.1:18080 -> proxy:8080`；
- `api:8000`、`postgres:5432` 不发布到宿主机；
- 禁止 `network_mode: host`、`privileged: true` 和 Docker socket 挂载；
- 不使用全局固定 `container_name`，依赖 Compose project 前缀隔离。

生产镜像必须不可变：

```text
flower-app:<git-commit-sha>
```

API 与 Worker 使用同一应用镜像、不同启动命令。每次发布在 `/srv/flower/releases/<git-sha>/` 保存 Compose、环境清单、migration 版本和镜像 ID/摘要；`/srv/flower/current` 指向当前发布。至少保留上一已验证镜像，禁止用 `latest` 作为回滚依据。

初始资源预算（是限制建议，不是性能承诺）：

| 服务 | CPU 上限建议 | 内存上限建议 | 初始并发 |
|---|---:|---:|---:|
| api | 0.25 CPU | 384 MiB | 1 process |
| worker | 0.40 CPU | 768 MiB | `JOB_MAX_CONCURRENCY=1` |
| postgres | 0.30 CPU | 512 MiB | 总连接初始≤30 |
| proxy | 0.05 CPU | 64 MiB | 轻量反代 |

部署后必须根据真实图片处理、Piper 回退和设备 API 尾延迟重新评估。当前 2 vCPU 主机不在本 MVP 同时新增本地大模型或持续云 ASR。

数据库迁移采用**显式一次性步骤**，不得在 API/Worker entrypoint 自动执行：

1. 启动/确认 `postgres` 健康；
2. 完成数据库和 uploads 备份；
3. 使用目标 release 镜像执行 `alembic upgrade head`；
4. 迁移成功后再启动/切换 `api/worker/proxy`；
5. 迁移失败则停止发布，不启动新版本。

其他要求：

- PostgreSQL、uploads 与备份存放在 `/srv/flower/shared/`，独立于 release；
- API 和 Worker 有健康检查；
- Worker 等待数据库健康后启动；
- 容器日志限额建议 `10MiB × 3`；
- `.env` 不进入 Git；
- `backup.sh`、`restore.sh`、`cleanup.sh` 可用；
- `cleanup.sh` 至少执行：临时图片过期清理、原始遥测保留清理、小时聚合完整性检查、过期命令/任务清理；
- Worker 定时执行 `trend_aggregation` 与存储水位检查；
- 剩余空间低于 1GiB 时产生 `STORAGE_LOW` 告警并拒绝新图片；
- 恢复流程必须在独立测试实例实际演练一次。

**共享宿主机发布前审计**：首次安装 Docker 或修改 Flower 网络前，必须记录并比较发布前后 `ss -lntup`、`systemctl ... --state=running`、`ufw status verbose`、`nft list ruleset`、`ip route show table all`、Tailscale、OpenVPN、现有 Nginx 与 aibot 连接状态。Docker 会修改 NAT/转发规则，不得把“UFW 开着”当成充分隔离。

# 18. 验收测试

## 18.1 硬件与安全

1. **ADS1115**：运行 `i2cdetect -y 1`，必须显示 `0x48`。
2. **土壤标定**：干湿基准差达到设定阈值，插入深度已标记。
3. **P451**：有水和缺水各连续读取 50 次，无误判。
4. **缺水禁泵**：缺水状态下连续下发 20 次命令，水泵启动次数为 0。
5. **泵开关**：连续执行 20 次开关，全部成功。
6. **重启误启动**：完成 10 次上电重启，水泵不得误启动。
7. **进程崩溃**：执行 `kill -9` 后，GPIO 控制信号和水泵在 **5 秒内**恢复为 OFF；重复 10 次全部通过，并记录最慢一次。
8. **流量标定**：3 次测量极差不超过平均值 15%。
9. **滴漏口径**：保存平均值与最大值；剂量估算使用平均值，最大值只用于安全验收。
10. **最低可控剂量**：已计算并保存；低于该值的请求被拒绝或显式上调并提示。
11. **防虹吸**：满桶、停泵 10 分钟，无连续水流，3次测试的最大滴漏不超过 3mL。
12. **摄像头**：连续 20 次拍照，至少 18 次通过质量检查。
13. **BLE**：30 分钟内持续更新；若不达标，必须完成有线备用切换。
14. **并发压力**：BLE 扫描和每分钟拍照持续 30 分钟，主控循环无阻塞。

## 18.2 状态模型

- 代码中没有第二套含义重叠的 `device_state`；
- `operating_mode` 只有四个合法值；
- `activity` 与 `fault_codes` 不改变自动化等级定义；
- SAFE_HOLD 下任何来源均不能开泵；
- LOCAL_CONSERVATIVE 只能执行本地 fallback_policy；
- UI 显示 operating_mode 和主要 fault 原因。

## 18.3 决策单一来源

- 完整决策算法只存在于后端一个模块；
- Pi 代码中不存在温度、天气、花盆、季节修正公式的复制；
- Pi 只解析和执行 fallback_policy；
- 相同输入得到相同输出；
- `soil < effective_min` 且在允许时间窗内时必定得到 `water`；
- 仅当低于 `URGENT_OVERRIDE_GAP_PCT` 时才允许越过时间窗；
- fallback_policy 时区缺失或非法时 Pi 拒绝执行；
- 所有关键分支有单元测试；
- LLM 输出不包含执行参数。

## 18.4 限额与时间恢复

- 时间不可信时不浇水；
- 开泵前预扣；
- 中断命令进入 provisional；
- 恢复后能用服务器时间对账；
- 无时间记录不会永久占用额度；
- 也不会在恢复后立即释放；
- 断电重启20次不能重置额度。

## 18.5 云端与共享宿主机

- [ ] Flower 仅发布 `127.0.0.1:18080`，API 8000 与 PostgreSQL 5432 无宿主公网绑定；
- [ ] 宿主 Nginx 仍是唯一 80/443 入口，City Front 原有路由无回归；
- [ ] aibot `nox-brain.service` 的运行目录、配置和服务未被 Flower 部署修改；
- [ ] Docker 安装/启动后 Tailscale、OpenVPN、UFW/nft 与现有服务连通性通过回归；
- [ ] `APP_ENV=production + DEV_AUTH_BYPASS=true` 时应用启动失败；
- [ ] `APP_ENV=production` 且 APP_BASE_URL 为 `http://` 时应用启动失败；
- [ ] 生产 migration 只由单一受控 job 执行，API/Worker entrypoint 不自动迁移；
- [ ] release 使用 commit SHA 固定镜像，可不重建直接切回上一 release；
- [ ] `/health` 为存活探针，`/ready` 验证数据库和 migration 状态；
- [ ] 定时备份存在、保留策略生效，并有一次独立测试恢复证据；
- [ ] 与 aibot 并行时 Flower 快速设备接口 p95 目标 <500ms，且正常语音体验劣化目标不超过基线20%；若未获得真实高峰证据则标为 NOT_RUN/BLOCKED，不得宣称通过。

## 18.5.1 云端功能

- 开发/测试环境可从空环境 `docker compose up -d --build` 启动；生产必须使用已记录的 commit-SHA 固定镜像和显式 migration，不在生产现场用 `--build` 作为发布方式；
- migration 幂等；
- API 和 Worker 健康；
- 同一命令并发领取100次只成功1次；
- 未领取命令超过 `claim_deadline_at` 后不可再领取；
- 已开始的 2-3 脉冲会话运行超过 60 秒时不得因领取 TTL 被中断；
- 超过 `session_deadline_at` 时 Pi 与服务端均能停止/标记 `timed_out`；
- Job 在 API/Worker 重启后恢复；
- 图片越权和非法文件被拒绝；
- 磁盘剩余空间低于阈值时图片上传被拒绝并产生告警；
- 一个设备无法插入第二条 `is_primary=true` 植物记录；
- 一个设备无法插入第二条活跃 `dispense` 命令；
- 备份可恢复。

# 23. 技术核验备注

1. Raspberry Pi 4 的四个 USB-A 端口连接到 VL805 USB 控制器；板载蓝牙使用 UART0 作为无线模块接口。因此“USB 摄像头和板载 BLE 共用同一 USB 总线”不是准确描述。仍需考虑 CPU、供电和软件任务并发。
2. 部分小米温湿度计库存固件的 BLE 广播加密，需要 bindkey 才能被动解析；软件必须先探测具体型号和加密状态，并准备有线温湿度传感器备用方案。

参考：

- Raspberry Pi 官方硬件与 UART 文档：`https://www.raspberrypi.com/documentation/computers/raspberry-pi.html`、`https://www.raspberrypi.com/documentation/computers/configuration.html`
- ESPHome Xiaomi BLE 文档：`https://esphome.io/components/sensor/xiaomi_ble/`

# 24. 项目核心价值总结

这个项目不是为了制造一台“看起来很聪明的水泵”，而是完成四层闭环：

1. **认知层**：知道眼前是什么植物；
2. **知识层**：知道它在当地通常怎样生长；
3. **感知执行层**：知道这一盆现在是否偏干，并在多重安全限制下少量补水；
4. **记忆层**：把家人的经验变成经过确认、仍可继续发挥作用的数字记忆。

v2.2 的工程取向是：

> 不确定时不行动；完整决策只有一个来源；真实数据与演示数据不混淆；软件安全必须建立在正确的物理结构之上。
